============================================================
TACSFON (OAUSTECH) — FULL-STACK WEBSITE EXECUTION SPECIFICATION
============================================================

PROJECT NAME
TACSFON (OAUSTECH)

OFFICIAL ORGANIZATION
TACSFON — The Apostolic Church Student Fellowship of Nigeria

CURRENT FELLOWSHIP IDENTITY
TACSFON (OAUSTECH)

CURRENT YEARLY THEME
"The Davidic Generation"

IMPORTANT:
The fellowship name, yearly theme, social links, contact information,
donation details, and other organizational information must be easy
to change without requiring changes throughout the UI components.

============================================================
1. ROLE
============================================================

You are a senior full-stack Next.js engineer and UI/UX designer.

Build a polished, production-ready website for TACSFON (OAUSTECH).

Do not build a generic church template.

The website should feel:

- modern
- welcoming
- youthful
- spiritual
- editorial
- clean
- natural
- elegant
- subtle
- trustworthy
- appropriate for a university Christian fellowship

The design should combine:

MODERN CHURCH
+
EDITORIAL DESIGN
+
NATURAL / ORGANIC VISUAL LANGUAGE

Avoid making the website look like:

- a generic SaaS dashboard
- a generic corporate website
- an old-fashioned church website
- an overly luxurious "premium dark" website
- an overly animated landing page

============================================================
2. PRIMARY OBJECTIVES
============================================================

The website should:

1. Introduce TACSFON (OAUSTECH).
2. Explain what the fellowship is about.
3. Communicate the current yearly theme.
4. Display fellowship activities and programs.
5. Display events and programs, including their flyers/images.
6. Explain the different fellowship units.
7. Provide useful information about TACSFON.
8. Allow visitors to contact the fellowship.
9. Allow visitors to access external social/community links.
10. Provide a donation interface.
11. Allow authorized administrators to manage dynamic events.
12. Provide a secure admin dashboard.
13. Be highly responsive.
14. Be accessible.
15. Be SEO-friendly.
16. Be friendly to search engines and AI/agentic browsing systems.

============================================================
3. NON-NEGOTIABLE TECHNOLOGY
============================================================

Use:

- Next.js
- App Router
- TypeScript
- Tailwind CSS
- shadcn/ui
- Zod
- React Hook Form
- Lucide React
- Framer Motion
- Supabase
- Brevo
- Express where backend separation is actually required/appropriate

Do not introduce unnecessary frameworks.

Use server-side functionality provided by Next.js wherever possible.

Do not create unnecessary backend infrastructure when a Next.js
Route Handler or Server Action is sufficient.

============================================================
4. DATABASE DECISION
============================================================

Supabase WILL be used.

Do not attempt to eliminate the database because the admin dashboard
requires persistent dynamic content.

Use Supabase for:

- administrator authentication
- dynamic event storage
- event images/files where appropriate
- required persistent dynamic data

Do NOT turn the project into a complicated CMS.

Keep the database intentionally small.

Static organizational content should remain outside the database.

============================================================
5. AUTHENTICATION
============================================================

Administrators use Supabase Authentication.

IMPORTANT:

There must NOT be a public administrator signup page.

Administrator accounts are created directly through Supabase.

The application should provide:

/admin/login

and authenticated administrator access to:

/admin

Logout must be supported.

Protect all admin routes.

An unauthenticated user must never be able to access admin functionality.

Do not expose Supabase service-role credentials to the browser.

Use appropriate Supabase security practices.

============================================================
6. ADMIN DASHBOARD
============================================================

Build a simple and clean administrator dashboard.

Do NOT over-engineer it.

Suggested structure:

/admin
/admin/login
/admin/events
/admin/events/new
/admin/events/[id]/edit

Dashboard should provide:

- overview
- event management
- account/logout functionality

The dashboard does not need:

- complicated analytics
- complicated CMS functionality
- unnecessary charts
- complex permissions systems
- unnecessary settings pages

============================================================
7. EVENT MANAGEMENT
============================================================

Events are dynamic.

Authenticated administrators can:

- create events
- edit events
- delete events
- publish/unpublish events

Event fields should include at minimum:

- title
- description
- date
- time
- location
- event image/flyer
- optional external link
- published status

Potential additional useful field:

- event category/type

Do not force every event to have every field.

Some events may be simple.

Some may be major programs.

The UI must accommodate both.

============================================================
8. EVENT IMAGE / FLYER SYSTEM
============================================================

Event images/flyers must be supported.

The event editor should make uploading an image simple.

Use Supabase Storage where appropriate.

Validate uploaded files.

Do not allow arbitrary unsafe file types.

The public event interface should display event flyers/images elegantly.

Images must not destroy the visual hierarchy.

Use Next.js Image wherever applicable.

============================================================
9. STATIC VS DYNAMIC CONTENT
============================================================

STATIC CONTENT:

- About TACSFON
- general fellowship information
- units
- fellowship identity
- general beliefs/information
- Bible quotes
- general descriptions
- footer information

- other organizational information

DYNAMIC CONTENT:

- events
- programs that administrators need to regularly manage
- event flyers
- event dates
- event descriptions
- event links
- published/unpublished status

Do not put every piece of content into Supabase.

============================================================
10. CONTENT FILE
============================================================

A separate content file will be provided by the project owner.

The file contains content direction and organizational information.

Do NOT expect the content file to contain every sentence required for
the website.

Use the provided content as the source of truth.

appropriate polished copy that stays faithful to TACSFON.

Do not invent organizational facts.

If information is genuinely unavailable, use a clearly identifiable
placeholder rather than presenting invented facts as real.

Make changeable content centralized.

Avoid hardcoding organizational information across dozens of components.

Example conceptual structure:

- hero images

- decorative images
- other assets

   ↓

   ↓
Rate limiting / abuse protection
   ↓
Brevo API
   ↓
Admin receives email
   ↓
Visitor receives confirmation email

The project owner will provide:

- Brevo API key
- sender email
- sender name
- receiving/admin email
- any other required credentials

============================================================
30. BREVO SECURITY
============================================================

BREVO API credentials MUST NEVER be exposed to the client.

Do not put Brevo credentials into:

- client components
- browser-accessible variables
- NEXT_PUBLIC_ environment variables
- source code

Use environment variables.

Example:

BREVO_API_KEY=
BREVO_SENDER_EMAIL=
BREVO_SENDER_NAME=
CONTACT_RECEIVER_EMAIL=

Use actual variable names consistently.

Never commit secrets to Git.

Provide/update .env.example with placeholders only.

============================================================
31. CONTACT CONFIRMATION EMAIL
============================================================

Do NOT write a robotic message such as:

The tone should communicate:

- gratitude
- warmth
- fellowship
- reassurance that the message was received

Do not make theological claims that aren't supported by the provided

32. RATE LIMITING
============================================================

- obvious abuse
- malformed requests
- oversized payloads

- admin input

- API keys
- Supabase service keys
- internal errors
- stack traces
- implementation details

Log useful errors server-side where appropriate.
